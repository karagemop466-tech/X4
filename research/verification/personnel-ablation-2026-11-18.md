# Personnel / availability ablation: what a waiver actually costs (2026-11-18)

Session `arena/dee8092e-x4`, task **T48**. The brief asks for
"injury and personnel ablations instead of fixed penalties" — *"test the same model with and
without the personnel features and report the difference with uncertainty"* — and separately
*"use snap counts as the starter proxy when the depth chart is unavailable"* and
*"model depth from playing time, not jersey order"*.

This document is the first **measurable** answer the repository has to that family of
requirements. It is deliberately narrow: it uses only data already committed and verified in
this repository, re-derives every number from the raw CSVs, and writes no model feature.

## 1. The gate that comes first (and why no personnel *model feature* ships today)

The brief's own rule is explicit: *"Do not build the feature until one route is verified for
all 32 clubs."* For a personnel term to be a front-loaded model feature (a points adjustment
applied to a *future* game), the system needs a starter/backup label for every club at
kick-off time.

| Route | State on 2026-11-18 | Verdict |
|---|---|---|
| (a) Club-published depth charts | 31 of 32 clubs transcribe to `data/depth-wk11-2026.csv` (1,558 rows). Houston publishes an image (F-24/F-46). 26 of 31 charts print no date (R-4). | **Not verified for all 32** |
| (b) Official snap counts (playing time) | Only one Game Book is captured (HOU at CLE, Week 10) — `data/houston-playtime-depth-wk10-2026.csv`. No league-wide official snap-count feed has been verified. | **Not verified for all 32** |

Neither route is complete, so **no fixed points penalty and no depth-slot feature is
published**, and this page does not add one. What *can* be done today, without any of that,
is the other half of the brief's instruction: measure, from data that already exists,
**how much a personnel event has actually cost the teams that suffered it** — and report it
with uncertainty — so the eventual feature is calibrated against evidence instead of a guess.

## 2. What is being ablated

There is exactly one availability dataset in the repository that is complete enough to
support measurement: the **official NFL.com Week 10 injury report**
(`data/injuries-wk10-2026.csv`, 347 player rows, captured from
<https://www.nfl.com/injuries/league/2026/reg10>). Every row carries a practice status and a
game status. 81 rows carry a **game designation** (70 `Out`, 11 `Doubtful`); 266 carry none.

The other availability dataset is the **official Week 10 outcomes**
(`data/games-2026.csv`, 14 finals), which are proved against the official standings by
`tools/verify.py`.

So the ablation question is: **do clubs that the official report rules a player `Out` for
score differently from clubs it does not?** That is the observable the report actually
supports. It is not "player X is worth Y points" — it is "a lost player of this kind is worth
a measured number of points, with an interval".

## 4. The two ablations the brief actually names

### 4a. Depth slot vs. no depth — not estimable today (this is the honest answer)

The brief's headline ablation is *"compare identical models with and without verified
availability features using chronological holdouts"*. Verified availability features do not
exist at the resolution required (a starter/backup label per club, at kick-off time). The
chronological holdout exists (weeks 3–10, 118 games), but there is no second model to hold
out. **Publishing a difference here would be inventing an ablation, so none is published.**
The gate that would change this is S5 (Houston) plus the 31-club verification in §1.

### 4b. Designation vs. no designation — estimable, and measured above

The measured table in §3 *is* the with/without test the data supports. Its limits, all of
which change how it must be read:

1. **n is small at the club level.** 14 playoff-relevant games are being cut four ways
   (designation × home/away). Any interval that spans zero means "cannot tell".
2. **Designation is not the same as absence.** A player listed `Out` on the report is a
   confirmed absence; a club with **no** designated player is not thereby at full strength —
   it may be resting a player, or the report may not cover him (reserve lists are a separate
   document; see F-43).
3. **The assignment is club-level, not player-level.** A club with two `Out` receivers is
   counted once. The player-level question — *how much does one lost starter cost?* — needs
   snap counts for **both** the replacement and the man he replaced, which exists for one
   club-week (Houston, §1b).
4. **A one-week cross-section is correlation, not causation.** A club can rule a player out
   *because* the game is already lost (Week 18 behaviour), or rule out a player who was not
   going to play. This is why the result is published as a *base rate to calibrate against*,
   never as a coefficient to add.

## 5. What the measurement licenses, and what it forbids

| Allowed by this evidence | Forbidden by this evidence |
|---|---|
| Quoting a measured points-per-designation base rate with its interval, as an input to a future prior | Adding "−N points per Out player" to a prediction |
| Sizing the *maximum* a personnel feature could plausibly move a Week-11 line | Claiming a depth-slot effect is "priced in" or "ignored" by the market |
| Setting the sample the next capture must reach before a feature is trusted | Publishing any personnel-adjusted fair line |

## 5a. Input verification (added after the first draft)

Because the whole comparison rests on four club-games, the official Week 10 report was
re-read from the **live** page on 2026-11-18 and every "clear" club was confirmed to carry
zero `Out` designations: **BUF, LV, NYG, PIT**. Three designated controls (SEA, CAR, HOU) and
CLE were re-read the same way and matched the committed CSV **row for row, including every
designation**. The full record, with the named players checked, is
`research/verification/personnel-ablation-live-check-2026-11-18.md`.

`tools/personnel_ablation.py` now asserts that each of those four clubs still has zero `Out`
rows before the page quotes them, so the page cannot publish a verification the data no
longer supports. Note what this does and does not do: it verifies the **input**, not the
finding. Both A1 and A2 intervals still span zero.

## 6. Reproduce

```bash
python3 tools/personnel_ablation.py           # rebuild the CSV + print the table
python3 tools/personnel_ablation.py --check   # fail if the committed CSV is stale
```

Outputs: `data/personnel-ablation-wk10-2026.csv` (one row per ablation with n, mean, SE, 95%
CI, and the exact source cells), and the rendered table on `site/personnel-ablation.html`.
